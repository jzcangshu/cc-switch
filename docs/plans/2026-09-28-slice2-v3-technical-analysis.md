## 1. 结论与证据等级

采用既有 `RouteWrite::Custom(Table)`（共享槽表写入变体）承载官方代理镜像，保持官方认证目标及空认证标记参数；不增加枚举成员，不修改契约算法、写入引擎或请求分派。

新增形状检查仅用于“是否允许把活动配置导入供应商或抽取片段”的保守读入边界。不得将其并入 `is_codex_live_taken_over`（旧接管识别函数），也不得传入启动恢复和数据库行污染判定。

| 判断                                   | 依据                                                                                 | 可以得出的结论                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 共享直连、共享代理使用相同默认历史过滤 | 桌面内置客户端 `0.158.0-alpha.2.1`（版本号）的真实应用服务器，独立配置目录和合成历史 | 对该版本，两种表形态均筛选共享标识，端点及双向长连接开关不会改变本次列表结果 |
| 两种共享形态均可恢复合成历史           | 同一客户端的会话恢复接口，无发送操作                                                 | 配置加载和恢复成功；不代表真实账号发送成功或所有客户端版本均兼容             |

源码定位以本基线为准；升级基线后应复核相关符号和测试，不把行号当作跨版本保证。

## 2. 需要掌握的结构

### 2.1 当前供应商不是单一指针

`mode/current.rs`（模式供应商解析）区分 `Purpose::Direct`（退出代理后使用的直连供应商）与 `Purpose::InUse`（当前请求目标）。`ProviderService::current`（供应商查询入口，4799 行）使用后者。

设置保存链为：

1. `commands/settings.rs:62`（设置保存）先保存开关。
2. `services/provider/mod.rs:70`（官方配置重应用）取得既有切换锁，恢复未完成操作，然后读取实际使用中的供应商。
3. `services/provider/live.rs:743`（按模式同步）在代理模式下调用已持锁的重同步入口。
4. `mode/controller.rs:225`（官方客户端代理写入）重新规划契约；摘要改变才写文件，否则只提交模式状态。

因此无需在设置入口套第二把切换锁，不应改为直接写配置文件。原函数注释“代理模式不受开关影响”在本修复后需要更新，函数编排本身无需改写。

### 2.2 表写入和认证是两个独立维度

`services/provider/codex_direct.rs:395`（官方代理规划）分别得到路由、认证标记参数和认证目标。普通官方账号选择 `AuthGoal::Official`（官方认证目标），托管账号选择 `AuthGoal::Managed`（托管认证目标），两者使用同一个路由分支。

`run`（执行写入，704 行）只有在认证标记参数为非空、且路由为共享槽变体时才调整认证字段。官方分支保持 `stamp = None`（不调整第三方认证字段），因此复用共享槽不会将官方镜像变为第三方认证。

共享槽变体已经覆盖选择器、空配置首次建表、普通表、内联表、契约计算。无需新增 `OfficialMirrorProxy`（曾提议的官方共享代理变体）。其注释应改为“写入共享槽的完整路由表；认证由规划方决定”，无需重命名枚举或推广为通用框架。

### 2.3 契约摘要是客户端要求的摘要

`contract_of`（契约计算，477 行）已覆盖共享槽的选择器和表。地址、模型及独有字段、目录摘要、目标托管账号、普通官方登录要求也进入摘要。`table_text`（表摘要准备，465 行）有意移除 `requires_openai_auth`（是否使用官方认证字段），这是既有约定，不应在本切片改变。

应保持以下关系：

- 开关开启导致旧代理选择器变为共享选择器，摘要不同。
- 本地代理地址改变，摘要不同。
- 客户端要求完全相同，摘要相同，既有“不读不写文件”优化保留。
- 托管目标账号不同，摘要不同；同账号的访问凭据更新不应仅因凭据字节改变摘要。

仅检查摘要中包含某个字段不够。诊断还调用真实重应用入口，核对开关往返、认证字节及相同契约下外部新增注释保持原样。

## 3. 为什么不能扩大通用接管识别

### 3.1 实际消费点比第二版清单多

`services/proxy.rs:317`（旧接管识别）同时被以下边界消费：

| 消费者                                       | 行为                                     | 是否允许使用新形状作为依据         |
| -------------------------------------------- | ---------------------------------------- | ---------------------------------- |
| `services/provider/live.rs:991`（导入守卫）  | 拒绝把代理投影存为供应商                 | 可以保守拒绝，但不得声称已证明来源 |
| `lib.rs:1926`（片段抽取守卫）                | 跳过代理投影                             | 可以保守跳过                       |
| `mode/controller.rs:751`（启动遗留判定）     | 设置接管状态，进而写回代理或直连投影     | 不可以                             |
| `mode/controller.rs:380`（直连行可用性判定） | 经静态配置检查判定行污染，可能退回空投影 | 不可以；第二版漏列                 |

不能通过搜索旧桶名出现位置就声称找全了消费点，还必须追踪包装函数和调用者。

### 3.2 可重复的误伤反例

设备模式为直连、未接管，没有备份；用户活动配置恰好与新镜像形态相同。把该形态加入通用识别后：

1. 启动将其认作旧版遗留接管。
2. 将本地模式视为已接管。
3. 代理开关为关时写回直连投影。
4. 原共享选择器被移除，官方镜像被替换成带占位符的休眠表。

反例测试不仅检查布尔值，还比较真实启动函数执行前后的完整配置。另一个测试把同形配置放进供应商行，证明其会被行污染检查拒绝。

对照中的匹配包含官方名称、认证、协议、关闭双向长连接和精确回环端点。继续缩紧字段匹配不能解决来源不可区分的问题。

### 3.3 新版崩溃恢复已有来源记录

`mode/operation.rs`（写操作）在首次发布前记录未完成操作、文件写前和写后摘要以及目标模式。`lib.rs:677`（启动）在默认供应商导入前调用恢复；片段抽取及模式启动更晚。

发布后、模式提交前的故障应交给现有记录恢复。状态正常时，已接管标志也会使旧版遗留检测被跳过。不能为了设备状态丢失、新数据库或用户手工复制配置这类“来源未知”场景，新增凭形状自动重写的授权。

存在外部修改或恢复失败时，沿用当前引擎报告行为；本切片不修改冲突、前滚、发布次序和锁结构。

## 4. 最小候选的读入保护

在 `services/proxy.rs`（代理服务）增加专用于导入的保守入口，例如 `live_has_proxy_import_risk`（活动配置存在代理导入风险）。只由供应商导入和启动片段抽取调用；其他应用原样委托现有判定。

对官方共享代理形态检查：

- 顶层选择器精确为共享槽。
- 对应表恰有五个生成字段，普通表及内联表均可读取。
- 名称为官方名称、响应协议、使用官方认证、关闭双向长连接。
- 地址可解析为普通超文本传输地址，具有主机，路径为版本一路径；不带用户信息、查询或片段。
- 不与当前数据库端口绑定。旧端口、指定网卡地址及第六版互联网协议地址也是应用可能生成的配置。

此检查是“可疑投影”识别，不是所有权证明。用户手工配置完全相同时，允许导入被拒绝，但不得改写活动文件、认定数据库行污染或自动恢复。错误文案应说明“与代理投影形态相同，无法安全导入”，不能谎称一定包含占位符。

读入守卫不承担任意手工改造后的代理配置识别。额外字段、改道配置或未知形态不应据此扩大自动写入权限。后续如需处理漂移，必须单独说明来源依据。

### 4.1 两处旧判断需要纠正

导入服务在读取配置后直接构造供应商并保存，凭据情况只影响分类。这里不存在第二版所称的 `keyless_fallback_error`（无凭据兜底错误）路径。基线实验使用空认证仍导入成功。

另一方面，片段抽取器已整体移除供应商表和关键字段。因此“守卫漏判一定把代理地址抽入片段”也不成立。新增守卫是维持“不从代理契约抽片段”的边界，不能夸大为已经证明的地址或凭据泄漏。

## 5. 客户端证据及适用范围

测试使用桌面安装中实际内置的 `0.158.0-alpha.2.1`（客户端版本），通过标准输入输出协议启动独立应用服务器。配置目录、状态数据库与三条合成会话均隔离；未使用真实认证，未发送模型请求。

三个会话分别标记为 `custom`（共享桶）、`openai`（原生官方桶）和 `cc-switch-official`（旧官方代理桶）。每种配置分别启动进程。

| 活动配置                             | 默认列表       | 显式不限制供应商 | 读取共享会话 | 恢复共享会话       |
| ------------------------------------ | -------------- | ---------------- | ------------ | ------------------ |
| 官方共享直连，无地址、开启双向长连接 | 共享桶一条     | 三条             | 成功         | 成功               |

## 6. 试验方法与结果索引

本轮直接编译完整仓库，在隔离工作树中加入内联诊断测试，没有提取并重写业务算法。数据库使用仓库的真实内存数据库，文件写入及恢复调用实际引擎，本地代理监听使用临时端口。托管账号为测试接口生成的合成账号，不联网登录。

源码实验保留在 `C:/Users/jzcan/.codex/worktrees/slice2-proof/cc-switch`（隔离工作树）；原始日志、合成历史和夹具在 `D:/cc-switch/.tmp-cluster/slice2-v3-proof`（本机证据目录）。可移植的脚本和测试随本文存入证据子目录。

实验分三组：

1. 基线：共享桶要求失败；无状态导入保护要求失败。真实重同步首次遭遇系统原子替换错误，单独重跑后明确失败于旧代理桶与共享桶不相等。其他结构对照通过。
2. 扩大通用识别的反例：手工活动配置保留、手工供应商行可用，两项均失败。
3. 最小候选：共享槽复用，加独立读入守卫。曾取得 12 项专用测试全部通过；另运行官方客户端相关筛选测试，702 项通过、1 项原有测试忽略；投影模块 6 项、写操作模块 18 项通过。不同筛选集存在重叠，不相加冒充独立测试总数。结果与日志见证据目录的验证结果记录。

诊断中曾把发布后故障点误写为不存在的名字，导致一次断言失败；已按引擎实际名称修正并重跑。这是测试编写错误，不记为产品缺陷。不能把最初失败日志隐去，也不能把修正前的运行算作恢复覆盖。

基线和候选出现系统错误 1175（系统无法删除被原子替换的旧文件），曾经同样代码重跑全部通过。之后增强“同契约不进入写入”的故障断言，再次运行得到 10 项通过、2 项原子替换错误。未通过增加产品重试或更换写入算法掩盖失败，也未继续反复重跑以获得绿色。该底层异常根因未定位，必须作为正式交付验证的未闭合项；不得将一次通过解读为并发文件写入已获绝对保证。

之后运行完整库测试：2905 项通过、1 项失败、10 项忽略。失败为另一客户端的默认代理端口绑定，单独重跑仍失败；只读确认默认端口已有监听，未停止现有进程。完整库结果不是全绿，也不是包含所有独立集成目标的全量验证，详见证据记录。

## 7. 后续执行者无需重新决策的事项

- 使用共享槽既有变体，不新增专用变体。
- 普通官方与托管账号都在功能范围内；不得排除托管账号。
- 不修改通用接管识别和静态行污染判定。
- 两个读入入口使用独立保守守卫；未知来源只阻止读入，不触发恢复。
- 使用已有契约摘要和重同步；不新增契约版本、不移除现有摘要字段。
- 既有第三方路由规范化、休眠表、配置档覆盖拒绝、认证权威规则原样保留。
- 被配置档引用的旧表保留；未引用的旧代理表沿既有逻辑清理。活动配置档选择旧代理标识时应拒绝目标投影，不要为通过测试放宽保护。
- 不给所有旧标识补固定官方别名，不在切换时迁移数据库，不改变请求清理或重试。
